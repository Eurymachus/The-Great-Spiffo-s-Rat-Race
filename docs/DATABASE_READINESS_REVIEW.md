# Database-readiness review

Recorded 25 November 2026 on `codex/rat-race-dev`, based on `fe855cad` plus
the local release-switch work. This is a source and migration-metadata review,
not production database acceptance or a cleanup proposal.

Follow-up: the owner subsequently authorized account-closure/retention work.
[RETENTION.md](RETENTION.md) records the implemented safeguards and remaining
gates. The findings below preserve the original review baseline; related-history
closure now uses a reviewed first-release redaction path; unsupported history
blocks rather than silently detaching ownership. Source-review findings below
describe the pre-remediation baseline, not the current implementation.

No existing database was queried, migrated, reset or changed for this review.
Migration metadata was loaded without a database connection; a SQL execution
guard rejected any attempted query. No schema or application changes were made.
Host schema versions, row counts, file inventories and retention jobs remain
unverified. Earlier disposable test results are identified separately below.

## Outcome and launch gates

There is no evidence that reducing table count is necessary for launch.
There are lifecycle, retention and rollout-preservation gaps to resolve before
opening the affected features. RR 2 restructuring remains deferred until its
export contract is final.

| Finding | Impact / required evidence |
| --- | --- |
| Account deletion does not establish anonymisation of retained records | Before accounts open: closure acceptance must cover all associated data and files, not just removal of the login row. Before RR 1.0 opens: prove closed ownership cannot revert to a historical public identity or become available for a new claim. |
| Approved retention schedule is not implemented end to end | Before accounts open: demonstrate registration-age deletion and an operational retention schedule, including holds, logs and backups. |
| Personal-data download omits first-release workflows | Before the affected intake opens: establish and test coverage of Workshop requests and RR 1.0 claims/results/updates. |
| Standard role bootstrap grants no RR 1.0 model permissions | Before RR 1.0 opens: prove intended non-superuser reviewers retain access after release preparation. |
| RR 1.0 ownership rules have alternative-write and concurrency gaps | Before RR 1.0 opens: test ordinary admin ownership edits and simultaneous claims on the host database engine. |
| Seed/import/reset tools are not generic populated-upgrade tools | Before rehearsal or deployment: establish exact tool scope, closed intake during replacement, preservation assertions and recovery evidence. |
| Migration graph is consistent, but historical paths have dependencies and destructive steps | Before rollout: record actual starting migration versions and test the relevant fresh and populated paths. |

These are findings and acceptance requirements. No repair design or deletion
proposal has been approved through this review.

## Inventory and apparent duplication

Django model metadata reports 86 managed project tables, including autogenerated
join tables and excluding Django's own tables: administration 1, branding 3,
pages 7, registry 54, zomboid_catalogue 13 and operations 8. `SubmissionAudit`
and `RunDataDangerZone` are proxies, not extra tables. No unmanaged project
models were found. This is a code inventory, not an inventory of tables on a host.

- `Participant.email` and `normalized_email` are both unique and converge through
  `Participant.save()`. Normalized email still has readers in forms, verification
  and administration. This is a possible later simplification, not an unused field.
- Inherited `first_name`, `last_name` and `date_joined` have no direct application
  references found outside migrations; `registered_at` is actively used.
  Framework behaviour remains relevant, so absence of direct readers is not proof
  these inherited fields can safely be removed.
- Run, participant, Workshop and legacy saved-view families have separate readers,
  writers and permission contexts in their workspace helpers. Their repeated
  structure does not make their records interchangeable.
- Branding retains direct image fields alongside managed-image references.
  Context processors still fall back to direct images. Removing either path
  requires an actual asset inventory and compatibility evidence.
- RR 2 raw submissions, evidence revisions, audit entries, projections and
  normalized authority records have different provenance and lifecycle roles.
  See `registry/run_review.py`, `registry/submission_approval.py` and
  `operations/run_moderation_reset.py`. A moderation reset explicitly clears
  authority and review state while retaining submissions. They are not proven
  duplicates. Contract-dependent restructuring is deferred.
- Catalogue entries, typed details, aliases and assets implement versioned
  reference data. Operational rate-limit and heartbeat tables are actively used.

No table or field is classified as safe to drop by this review.

## Relationships, deletion and ownership

Evidence: `registry/models.py`, `registry/admin.py`, `registry/leaderboard.py`,
`registry/views.py`, `registry/legacy_admin_workspace.py`, saved-view helpers,
and the branding, pages, operations and catalogue model definitions.

Account closure creates a non-personal receipt and calls `Participant.delete()`.
The normal participant admin delete action is disabled. Account deletion cascades
to provider accounts, notifications, ownership claims and personal view
preferences. Run owners, reviewers, Workshop submitters/voters and saved-view
owners generally become null. Results and submissions therefore survive, but
nulling an owner is not sufficient anonymisation.

For RR 1.0 specifically, `LegacyRun.claimed_participant` becomes null and the
participant's `LegacyRunClaim` is deleted. The retained run still contains its
historical name; rankings fall back to that name when there is no claimant.
Evidence URLs, titles and original import CSV also survive. The claim path
checks current ownership and claims, so this deletion graph permits the run to
look unclaimed again. This is source-derived behaviour, not a reproduced host
incident. The existing account-closure test checks account removal and receipt,
not this related-data lifecycle.

Workshop reasons, review notes and retained source/evidence payloads can contain
identifiers independently of their nullable user links. Their contents cannot
be certified anonymous without a specific lifecycle treatment.

Avatar and quarantine files are deleted before the account's database deletion
completes. Database rollback cannot restore those files. Future queryset-based
retention deletion would also bypass the model's instance `delete()` override.
File cleanup and database failure handling require explicit acceptance.

Ownerless private saved views survive account deletion, but their queries still
require shared status or the current owner. They do not automatically become
public. Retained filter values nevertheless belong in the retention inventory.

Protected references include legacy submission import provenance, managed images,
catalogue references and operational job sources/schedules. Protection can block
cleanup; deleting a parent is not a universal way to remove its dependencies.
Parent-owned content and run detail records also use cascades. Test both blocked
deletes and intended cascades, including external files, in an isolated database.

RR 1.0 ownership has only pair uniqueness on `(run, participant)` for claims;
there is no database-wide one-pending-claim-per-participant constraint.
The claim request locks the target run, so concurrent requests for different
runs by the same participant need a database-engine concurrency test.
The approval path has additional locking and checks, including a joined
participant; this review does not conclude approval has the same race.
Separately, `LegacyRunAdmin` exposes `claimed_participant` for ordinary edits,
outside the claim-review action and its checks/audit trail.

## Fresh-install migrations and seed dependencies

Offline migration loading found no graph conflicts. Comparing final migration
state with registered models found no pending model changes. The registry merge
leaf is `0075_merge_reading_cooked_food`, which depends on `0071` and `0082`;
filename number alone does not determine migration order.

Historical dependencies still matter:

- Registry `0029` reads packaged `data/legacy_hall_of_fame.json`.
- Registry `0032` removes the older legacy tables and creates the replacement
  schema without a record transfer. A populated installation crossing this
  migration cannot be assumed to preserve old legacy records.
- Registry `0047` imports current review/model code for its populated-data path.
  Passing an empty install does not prove that path works after future refactoring.
- Registry `0050` backfills evidence revisions; its reverse removes revisions.
  A successful forward migration does not establish lossless rollback.

Earlier release-switch tests created disposable SQLite databases. The relevant
suite passed 388 of 394 tests; the six failures reproduce on unchanged `fe855cad`.
Those results do not establish fresh PostgreSQL installation or a populated
upgrade. The already-recorded production static-manifest startup failure remains
a shared installation blocker, separate from model/migration consistency.

`bootstrap_roles` replaces each standard group's permission set. None of those
sets includes RR 1.0 model permissions; `sync_staff_status` only updates staff
status. Direct user permissions and superuser access are separate, so this does
not mean every current reviewer loses access. It does mean the standard release
bootstrap does not establish the intended RR 1.0 reviewer capability and can
remove manually added group permissions. Test the actual intended roles.

## Populated upgrades and replacement tools

Evidence: `registry/legacy_imports.py`, `pages/site_presentation.py`,
`registry/management/commands/reset_legacy_rehearsal.py` and the Windows
release preparation/startup scripts.

Legacy import application preserves its review/source record but replaces all
legacy runs. It refuses replacement when claims or participant submissions exist.
That guard is useful, but a transaction and review-row lock do not by themselves
serialize a separate claim request or a second import. Manually assigned ownership
without a claim also falls outside that guard. Handover must be rehearsed with
intake closed and concurrent writers accounted for.

Presentation import excludes accounts and submission data but replaces pages,
navigation and exploit rulings, updates challenge-mode scalar fields and aliases,
and prunes themes/images outside the package. Challenge-mode fields are exported
generically, not limited to visual copy. It is an approved-content replacement
tool, not a harmless merge for every populated upgrade. Protected image references
and non-transactional file writes also need failure-path checks.

The staging-only legacy reset is scoped to legacy rehearsal data and defaults to
preview. It is not a whole-site clean-install reset and does not replace the
separately authorized staging reset procedure. RR 2 moderation reset is also a
different operation; neither belongs in ordinary live upgrade preparation.

Release preparation runs migrations, role bootstrap and static collection.
The staging installer invokes preparation before stopping old processes, so an
incompatible migration requires an explicit write-control/recovery rehearsal.

Required preservation evidence in disposable local copies, then hosted staging:

1. Record starting migration versions and representative accounts, provider
   credentials, role permissions, Workshop requests/votes/rulings, RR 1.0 imports,
   claims/results/pending reviews, and unrelated records and files.
2. Rehearse a fresh install with approved seed content and all switches closed;
   exercise enabled first-release journeys with RR 2 still off.
3. Upgrade a populated fixture and compare identifiers, ownership, values,
   credentials, evidence, moderation history and media before/after.
4. Exercise closure, retention, rejected deletes, concurrent claims/imports and
   interrupted file/database work on the intended database engine.
5. Prove recovery of matching database, media, code and configuration, including
   protection against restoring previously deleted identity. Do not assume reverse
   migrations provide this recovery.

No host state or backup recovery has been verified by this source review.

## Retention and data access

The approved schedule in `RETENTION.md` requires deletion of unverified accounts
30 days after registration. `expire_pending_registrations` changes status using
the latest verification-email time; it does not perform that deletion.

The two-year moderation/evidence schedule, 90-day logs and rolling 30-day backups
still require operational evidence and hold handling. The raw CSV fields in
`LegacyDataImport` retain source contents even when the parser ignores particular
columns. Include them, evidence payloads, historical names, notes and ownerless
saved-view filters in the personal-data inventory.

`operations/runtime_state.py` expires rate-limit buckets logically and resets
reused keys, but no global purge of expired database buckets was found. Unique
keys can accumulate on the database-backed deployment. Heartbeats reuse stable
keys and are a different lifecycle. This is an operational retention/growth
finding, not a reason to remove the runtime-state table.

`download_my_data` exports account/provider/notification information and RR 2
run/submission summaries, but omits Workshop requests and RR 1.0 claim/update
records. Coverage must match the features being opened.
